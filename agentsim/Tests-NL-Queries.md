Test 1 — Threshold boundary on goodwill credit auto-approval.
State: customer C-100 exists, account A-100 active, no restrictions, vulnerable_flag=false, recent_goodwill_credit_total=0. The proposed tool call is apply_goodwill_credit(customer=C-100, amount_pence=10000, reason=...). Expected: ALLOW. Then re-run with amount_pence=10001. Expected: BLOCK, unsat core references the rule "a call to apply a goodwill credit with an amount greater than ten thousand pence requires human approval." Validates: numeric threshold is exclusive at 10000, the rule fires at 10001, off-by-one is correct.

Test 2 — Rolling-window accumulator enforcement.
State: customer C-101, account A-101 active, vulnerable_flag=false, recent_goodwill_credit_total=49500. Proposed call: apply_goodwill_credit(customer=C-101, amount_pence=400). Expected: ALLOW (total would become 49900, still under 50000 threshold and under 10000 single-call threshold). Re-run with the same call after updating recent_goodwill_credit_total=50100. Expected: BLOCK, unsat core references "a call to apply a goodwill credit is not permitted if the customer's recent goodwill credit total exceeds fifty thousand pence." Validates: the precomputed accumulator field is read correctly, and the threshold check is "exceeds" (strict), not "at least."

Test 3 — Hard restriction overrides everything else, including approved disputes.
State: customer C-102, account A-102 with active restriction of type SANCTIONS_BLOCK, transaction T-102 status POSTED, dispute D-102 referencing T-102 with status APPROVED. Proposed call: apply_refund(transaction=T-102, refund_type=DISPUTE_REFUND, amount_pence=2500, reason=...). Expected: BLOCK, unsat core includes "a call to apply any refund or goodwill credit is not permitted if the affected account has any active restriction of type SANCTIONS_BLOCK." Validates: the SANCTIONS_BLOCK rule overrides the otherwise-valid dispute-approved refund path. Confirms cross-domain interaction is enforced.

Test 4 — Vulnerable customer gating with consumer duty assessment.
State: customer C-103 with vulnerable_flag=true, account A-103 active, transaction T-103 POSTED, no restrictions, no consumer duty assessment exists for the current interaction. Proposed call: apply_refund(transaction=T-103, refund_type=MERCHANT_REFUND, amount_pence=3000, reason=...). Expected: BLOCK, unsat core references "a call to apply a refund of any type where the affected customer has a vulnerable flag set to true requires that a consumer duty assessment exists for the current interaction." Then add a consumer duty assessment for the interaction with both checks passed and rerun. Expected: ALLOW. Validates: the vulnerable-customer gate is enforced, and once satisfied, the call proceeds.

Test 5 — Time-window dispute eligibility via precomputed field.
State: customer C-104, transaction T-104 status POSTED, days_since_posted=119, no other disputes. Proposed call: initiate_dispute(transaction=T-104, dispute_type=UNAUTHORIZED, customer_statement=...). Expected: ALLOW. Re-run with days_since_posted=121. Expected: BLOCK, unsat core references "a call to initiate a dispute of type UNAUTHORIZED requires that the referenced transaction's days since posted is at most one hundred twenty." Validates: the precomputed days-since field is consulted, and the threshold is inclusive at 120.

Test 6 — Section 75 amount range.
State: customer C-105 with KYC VERIFIED, transaction T-105 POSTED with section_75_eligibility=true. Run three proposals of initiate_dispute(transaction=T-105, dispute_type=SECTION_75) with the transaction amount varied across runs: amount=9999, amount=10000, amount=30000000, amount=30000001. Expected: BLOCK, ALLOW, ALLOW, BLOCK respectively. The two BLOCKs should reference "a call to initiate a dispute of type SECTION_75 requires that the referenced transaction amount is at least ten thousand pence and at most thirty million pence." Validates: range check is inclusive at both endpoints, and both endpoints behave correctly.

Test 7 — Conjoint blocking from multiple rules with multi-rule unsat core.
State: customer C-106 with KYC FAILED and sanctions_flag=true, account A-106 status FROZEN. Proposed call: apply_refund(transaction=T-106, refund_type=MERCHANT_REFUND, amount_pence=500). Expected: BLOCK. The unsat core should reference at least: the FROZEN-account rule, the FAILED-KYC rule, and the sanctions-flag rule. Validates: the validator returns a meaningful multi-rule core when many rules apply simultaneously, and the explanation surfaces all of them rather than just the first found.

Test 8 — COURT_ORDER restriction is permanent.
State: account A-107 with active restriction R-107 of type COURT_ORDER, requires_human_to_lift=true. Proposed call: lift_account_restriction(restriction=R-107, reason=...). Expected: BLOCK, unsat core references "a call to lift an account restriction of type COURT_ORDER is not permitted under any circumstances." Then rerun with the restriction's requires_human_to_lift flag changed to false. Expected: still BLOCK, unsat core still references the COURT_ORDER rule (not the requires-human-to-lift rule). Validates: absolute prohibitions take precedence over conditional ones, and the unsat core identifies the strongest rule, not the weakest.

Test 9 — Confirmed fraud blocks the dispute path entirely.
State: customer C-108, transaction T-108 POSTED, fraud report F-108 of status CONFIRMED referencing T-108. Proposed call A: initiate_dispute(transaction=T-108, dispute_type=UNAUTHORIZED). Proposed call B (after creating an APPROVED dispute D-108 in setup): apply_refund(transaction=T-108, refund_type=DISPUTE_REFUND, amount_pence=1500). Expected: BLOCK for both. Call A's core references "a call to initiate a dispute is not permitted if a fraud report with status CONFIRMED references the same transaction." Call B's core references the analogous DISPUTE_REFUND rule. Validates: the fraud-confirmed cross-cutting block applies to both the dispute initiation path and the refund path. Cross-domain interaction confirmed.

Test 10 — Negative test: a fully clean refund should proceed.
State: customer C-109 with KYC VERIFIED, vulnerable_flag=false, sanctions_flag=false, recent_goodwill_credit_total=0, recent_dispute_count=0, account A-109 status ACTIVE, no restrictions, transaction T-109 status POSTED with amount 5000, no fraud reports. Proposed call: apply_refund(transaction=T-109, refund_type=MERCHANT_REFUND, amount_pence=5000, reason=...). Expected: ALLOW with empty unsat core and no rules in the "rules consulted" set marked as violated. Validates: the validator does not over-block; clean cases pass cleanly. This is the most important test in the suite because false positives kill agent UX, and it's the easiest test to forget.
