# NL→SMT-LIB Pipeline — Control Flow (v3)

## Purpose

End-to-end control flow for the NL→formal-logic policy-model pipeline, v1. Defines the contract between the WFM stage (upstream, assumed complete) and the formalization + commit stages (defined here).

**Approach:** LLM-first, progressive hardening. Minimal symbolic machinery at v1. The "registry" is not a separate artifact — it is the policy model codebase itself. Persistent memory, queryable indexes, and contradiction tooling are deferred until scale demands them.

**Scope of logic:** decidable many-sorted FOL per `pipeline_spec.md` (enums, equality, connectives, bounded quantifiers, declared functions with known signatures, bounded integer arithmetic, cardinality constraints). No transitive closure, recursion, temporal reasoning, higher-order, or unbounded domains.

---

## Key design decisions

1. **Output language is SMT-LIB**, not Z3 Python API. SMT-LIB is the canonical stored form. Python-API conversion happens lazily at query time if programmatic access is needed.

2. **The policy model is one file: `policy_model.smt2`.** All declarations and all assertions live together. Each assertion is preceded by a structured comment carrying `bundle_id`, `rule_id`, `line_index`, and the original NL statement.

3. **No separate registry in v1.** The file IS the policy model. Reuse decisions are made by the formalizer LLM with full codebase context, not by a separate registry agent.

4. **Two repair loops, sequential not nested:** syntax repair (formalizer ↔ Z3 parser) then semantic repair (formalizer ↔ critic).

5. **Always produce, critic gates.** The formalizer never refuses. The critic is the quality gate.

6. **Atomic append-on-commit.** Each accepted bundle appends a contiguous block of lines. Commit is one atomic file write (staged write + rename).

7. **Rule granularity matches WFM decomposition.** One accepted sub-statement from WFM = one `rule_id` = one NL rule, regardless of how many SMT-LIB assertions it produces.

8. **Hard cap on policy model size for v1 testing:** 50 NL rules total. Cap check runs before accepting a new bundle.

---

## ID generation (explicit contract)

**`bundle_id`** — generated by orchestration at the moment the WFM confirmation package is accepted by the user. Propagates through the entire pipeline. Stable from that moment on, regardless of whether the bundle ultimately commits or fails.

**`rule_id`** — generated by orchestration immediately after the size-cap pre-check passes, before the formalizer runs. One `rule_id` per IN_SCOPE line in the bundle. Assigned in `line_index` order. Passed to the formalizer so it can include them in metadata comments.

**Policy on failed-bundle IDs:** If a bundle fails (any category), the pre-generated `rule_id`s are recorded in the bundle record but never appear in `policy_model.smt2`. They are effectively unused. Do not recycle them. New submissions (even re-submissions of the same NL) get fresh IDs.

**ID format:** implementation-defined (e.g., `b_0001`, `r_0001`, or UUIDs). Must be globally unique across the system's lifetime. Once generated, immutable.

## Repair loops — detailed contract

### Loop 1: Syntax repair

- **Trigger:** Z3 fails to parse the in-memory concatenation (existing file + new block).
- **Feedback to formalizer:** the raw Z3 parse error plus the new SMT-LIB block. The existing file content was previously validated on its own commit; errors are therefore attributable to the new block.
- **Budget:** 3 iterations. Threshold: any parse failure triggers an iteration; no "minor vs major" distinction.
- **Exit states:** parse succeeds (→ proceed to semantic critic) OR budget exhausted (→ bundle fails with `SYNTAX_FAIL`).

### Loop 2: Semantic repair

- **Trigger:** critic returns at least one objection. Any single objection triggers repair; no severity filtering.
- **Feedback to formalizer:** critic's structured objection list (see "Critic output shape" below).
- **Budget:** 3 iterations.
- **Syntax re-check inside Loop 2:** each new SMT-LIB is re-parsed once. If it fails to parse, that iteration counts against Loop 2's budget. Loop 1 does NOT re-engage from inside Loop 2.
- **Exit states:** critic approves (→ commit) OR budget exhausted (→ bundle fails with `SEMANTIC_FAIL`).

### Global per-bundle cap

Maximum 6 iterations total across Loop 1 and Loop 2. This is a natural consequence of the two budgets (3 + 3); stated explicitly so the behavior is unambiguous.

---

## Failure categories

When a bundle fails, the bundle record carries a structured reason:

| Category | Meaning |
|---|---|
| `SIZE_CAP_REACHED` | Committing would push total rule count above 50; bundle rejected before formalization |
| `SYNTAX_FAIL` | Loop 1 budget exhausted; formalizer could not produce parseable SMT-LIB |
| `SEMANTIC_FAIL` | Loop 2 budget exhausted; critic's objections could not be resolved |

All categories are terminal for the bundle in v1. No partial commit of successful lines within a failed bundle.

## File structure

### `policy_model.smt2`

The entire policy model. Single file. Grows by append-only commits. Every accepted bundle adds a contiguous block.

**Normative comment format for v1** (not merely suggested — the cap-check and audit tooling depend on this):

```
; ============================================================
; Bundle: b_0001  |  Committed: 2026-04-20T12:00:00Z
; ============================================================
; Rule: r_0001  |  Line: 0
; NL: "A traffic light is exactly one of red, amber, green"
(declare-datatype Color ((red) (amber) (green)))
(declare-sort TrafficLight 0)
(declare-fun color-of (TrafficLight) Color)
; [asserts for r_0001]

; Rule: r_0002  |  Line: 1
; NL: "If a vehicle is registered then it is not scrapped"
; [asserts for r_0002]

; ============================================================
; Bundle: b_0002  |  Committed: 2026-04-20T14:30:00Z
; ============================================================
; Rule: r_0003  |  Line: 0
; NL: "..."
; ...
```

**Parsing rules for cap check and audit tooling:**
- Bundle headers match regex `^; Bundle: (\S+)\s+\|\s+Committed:`
- Rule headers match regex `^; Rule: (\S+)\s+\|\s+Line: (\d+)`
- NL lines match regex `^; NL: "(.+)"$`
- Counting distinct `rule_id` values = counting unique matches of the Rule header regex

### `bundles/{bundle_id}.json`

One file per bundle, committed or failed. Format:

```json
{
  "bundle_id": "b_0001",
  "accepted_at": "2026-04-20T11:59:58Z",
  "committed_at": "2026-04-20T12:00:00Z",
  "pipeline_status": "committed",
  "rule_ids": ["r_0001", "r_0002"],
  "out_of_scope_line_indices": [2],
  "wfm_payload": { /* full WFM handoff: per-line statement_nl, agent3_verdict, scope/diff reports */ },
  "failure_reason": null
}
```

For failed bundles:
- `pipeline_status` is `"failed"`
- `committed_at` is `null`
- `rule_ids` still lists the pre-generated IDs (never used in `policy_model.smt2`; retained for audit)
- `failure_reason` is an object: `{"category": "SYNTAX_FAIL" | "SEMANTIC_FAIL" | "SIZE_CAP_REACHED", "detail": "<last error or last objection list>"}`

### `bundles/{bundle_id}.log.jsonl`

Per-iteration log. One JSON line per repair iteration. Written append-only during the run.

Each line:

```json
{
  "bundle_id": "b_0001",
  "timestamp": "2026-04-20T11:59:59.234Z",
  "loop": "syntax" | "semantic",
  "iteration": 1,
  "input_to_formalizer": { "error_or_objections": "..." },
  "formalizer_output_smtlib": "...",
  "check_result": "pass" | "fail",
  "check_detail": "<parse error or objection list>"
}
```

Purpose: debugging failures, observing patterns for progressive hardening, calibrating budgets. Not used by any runtime logic.

## Rule counting

**Unit:** one accepted sub-statement from WFM = one NL rule = one `rule_id`.

**Cap check:** before accepting a bundle, count distinct `rule_id` values currently in `policy_model.smt2` by scanning Rule header comments (regex above). If (current count + new bundle's IN_SCOPE line count) > 50, reject the bundle with `SIZE_CAP_REACHED`.

**Why NL-rule not assertion:** one NL rule may produce multiple `(assert ...)` statements in SMT-LIB (cardinality constraints, exactly-one-of encodings, etc.). Counting assertions would create incoherent half-commits. The rule_id is the atomic commit unit.

---

## Empty policy model case

On the first bundle (`policy_model.smt2` does not exist or is empty):
- Formalizer receives an empty codebase context.
- No reuse is possible; everything is new.
- Critic has nothing to cross-check reuse against but still reviews NL/SMT-LIB semantic match.
- Commit creates the file for the first time (same atomic write, just nothing to read first).

No special-case branching needed; the flow handles this naturally.

---

## OUT_OF_SCOPE lines

WFM marks some lines as out-of-scope. These:
- Skip formalization entirely.
- Do not receive a `rule_id`.
- Are retained in the bundle record (`bundles/{bundle_id}.json`) under `out_of_scope_line_indices`, with the line's WFM report available via `wfm_payload`.
- Do not count toward the 50-rule cap.

## Inputs and outputs by stage

For the implementing LLM's reference:

**Formalizer input:**
- WFM bundle (IN_SCOPE lines with `statement_nl`, `line_index`, and orchestration-assigned `rule_id`)
- Full current `policy_model.smt2` content (or empty string if file doesn't exist)
- System prompt (reuse guidance, style, examples) — content TBD, see "Deferred: prompts"

**Formalizer output:**
- SMT-LIB block for the bundle: new declarations (if any) + new assertions, with normative metadata comments (see "File structure" above)

**Syntax check input:**
- In-memory concatenation: `existing_file_content + "\n\n" + new_block`

**Syntax check output:**
- `{"pass": true}` OR `{"pass": false, "error": "<Z3 parse error string>"}`

**Critic input:**
- WFM NL for the new bundle
- Proposed SMT-LIB block for the new bundle
- Existing `policy_model.smt2` (for reuse review)

**Critic output shape:**
```json
{
  "approved": true | false,
  "objections": [
    {
      "rule_id": "r_0002",
      "line_index": 1,
      "issue_type": "nl_mismatch" | "inappropriate_reuse" | "silent_merge" | "other",
      "description": "<free-text explanation>",
      "suggested_fix": "<optional free-text hint>"
    }
  ]
}
```
If `approved` is true, `objections` is an empty list. If false, at least one objection is present.

**Commit input:**
- The in-memory concatenation that just passed both checks
- Bundle metadata (bundle_id, rule_ids, NL statements, timestamps)

**Commit output:**
- Updated `policy_model.smt2` (atomic write: write to `.smt2.new`, then rename)
- Updated `bundles/{bundle_id}.json` with `pipeline_status: "committed"` and `committed_at`

## What v1 does NOT include

Listed so the dev plan doesn't accidentally include these:

- No separate registry artifact (registry = the SMT-LIB file itself)
- No tool-using registry agent
- No semantic search / embeddings
- No structured identifier naming rules (A–G from earlier design) — naming is handled via formalizer prompt guidance, not programmatic gates
- No Z3 Python API generation in the commit path (SMT-LIB only; Python conversion is lazy, at query time)
- No per-line partial commit within a failed bundle
- No user-facing review UI or approval gates
- No graph-shaped edges, rule-level embeddings, or committed_edges
- No draft-vs-committed distinction in storage
- No contradiction detection (deferred)
- No cross-bundle consistency audit
- No truncation/summarization of the policy model when passing it to the formalizer (not needed at 50-rule cap; becomes relevant only when context-window pressure emerges)

---

## Accepted limitations

Explicit acknowledgments of where v1 trades rigor for simplicity:

1. **Semantic critic is judgment, not proof.** An LLM reading SMT-LIB and NL to judge equivalence is doing a vibes-check. It will miss things. Repair loops catch some misses, not all.

2. **Silent semantic merging is possible.** The formalizer might reuse an existing declaration when the new NL actually meant something subtly different. The critic is supposed to catch this but is not infallible.

3. **Size cap is conservative and arbitrary.** 50 rules is a starting point for observing behavior. If the formalizer and critic hold up cleanly at this size, evidence-based scaling is the next step.

4. **Whole-bundle failure is coarse.** If one rule in a bundle causes repair loops to exhaust, the whole bundle fails. Acceptable at v1 scale; revisit if observed data suggests per-line commit is warranted.

5. **No persistent memory structure beyond the file.** Queries over the policy model at v1 are manual (read the file, grep, inspect). This is sufficient for 50 rules. It is not sufficient for thousands; addressing that is deferred.

6. **Cross-bundle reuse quality depends entirely on formalizer prompting.** There is no programmatic naming discipline. If the formalizer drifts stylistically across runs, the policy model accumulates inconsistency. This is the primary quality risk in v1 and the primary signal to watch during testing.

---

## Deferred to later versions

- Separate registry artifact with structured fields and embeddings (when scale demands queryable memory)
- Graph-shaped edges with relationship labels (for contradiction detection)
- Programmatic naming rules (Rules A–G equivalent) (when drift is observed)
- Per-line commit with per-line failure categories (when observation shows many bundles would benefit)
- Z3 Python API conversion pipeline (when programmatic query access is actually needed)
- Automated contradiction detection (when policy model is mature enough to contradict itself meaningfully)
- Context-window management strategies (when model size approaches formalizer/critic context limits)

---

## Deferred: prompts

Prompts for the formalizer and the critic are TBD. They are the single largest factor in whether v1 works in practice, but they are a separate workstream from the control flow defined here.

Minimum prompt requirements to be specified during implementation:
- **Formalizer:** SMT-LIB only (no Python), reuse existing declarations where appropriate, naming conventions, examples of correct output for each scope construct, normative metadata comment format.
- **Critic:** what counts as a semantic issue, what counts as inappropriate reuse, the structured objection shape defined in "Critic output shape."
